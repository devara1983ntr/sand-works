# AUDIT LOG INTEGRITY — V1 (Phase 0.75)

## Decision
Audit events are generated by **trusted backend (Cloud Functions / server triggers)**, never by client-controlled writes. Client may only READ audit logs (owner). Rationale: a client can be modified/forged; a truthful audit must be written atomically by the mechanism performing the operation.

## When an audit event is generated
- Owner-privileged operations (server-authoritative): create session, create trip, attendance record/correction, delete (soft, trip/session/catalogue), close session, settings change, labourer/driver/vehicle create/edit/inactivate, profile change of owner identity fields, account operations (password change, delete-my-data, export), backup/restore, restore rollback.
- Auth events (server/Auth side): sign-in, password reset, account disabled, account delete — where available, captured at backend boundary.
- Never logged: secrets, tokens, raw passwords, full phone lists where avoidable.

## Audit event record fields
`eventId`(opId) · `actorUid` (server = request.auth.uid) · `actorRole` · `action` (enum) · `targetType` · `targetId` · `orgId` · `previousState`(opt map) · `newState`(opt map) · `reason`(opt) · `createdAt`(server timestamp) · `requestContextId`(opId) · `source`(CF/schedule/manual/auth).
Optional non-PII client meta may be added only at the server boundary, never client-authoritative.

## Integrity
- Append-mostly; rules: **client may not write or delete** `auditLogs` (rules deny direct client write/delete). Read: owner only (V1). Deletion: only via a governed purge job per retention (D-8), never client.
- Atomicity: audit write is committed in the same server transaction/CF invocation as the operation it records where feasible; otherwise a compensating server writer guarantees an event exists for every privileged action (tested).
- No silent history rewrite: corrections to attendance also write an immutable attendance event (see ATTENDANCE-INTEGRITY) that is separate from the admin audit log but shares ids.

## Retention & access
- Retention window: default 12 months for admin audit; confirm with owner (D-8). Labourer/driver records longer via soft-delete.
- Read access: owner viewer N-36 (filters by actor/action/date/type; shows before/after). V1 single owner; ADMIN/readers deferred.
- PII: audit may reference actor display name resolution in-org only; never embed secrets.

## Generation ownership
CF-only. Any operation that is not routed through CF but still privileged (e.g., a direct Firestore write the rules allow for owner) must itself be written via CF so the audit is guaranteed. Rules deny privileged field writes from the client (SERVER-AUTHORITY-MATRIX).

## Tests
FT-AUD: (1) each audited op → exactly one truthful audit row (before/after/reason), (2) a client trying to write/delete auditLogs is rejected by rules, (3) corrections produce both attendance event and admin audit, (4) retention purge job scoped.
